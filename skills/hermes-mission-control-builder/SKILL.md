# Hermes Mission Control Builder

Scaffold a privacy-minimized, read-only Hermes Desktop operations view from a versioned template. It creates a plugin file only; it performs no config edits and does not enable or reload the plugin.

## When to Use

- Use to stage Mission Control in an explicit sandbox home.
- Use after reviewing `references/SPEC.md` and `references/security-boundaries.md`.
- Do not use to expose a dashboard publicly, mutate operational data, or install into a live profile without approval.

## Prerequisites

- Python 3.9 or newer.
- A dedicated sandbox directory for initial generation and validation.
- **GREENLIGHT REQUIRED** before targeting a live Hermes home.

## How to Run

From this skill directory, use `python3` on macOS/Linux:

```text
terminal(command="python3 scripts/build_mission_control.py --hermes-home /approved/sandbox --dry-run")
terminal(command="python3 scripts/build_mission_control.py --hermes-home /approved/sandbox")
```

On Windows, use the Python launcher:

```text
terminal(command="py -3 scripts/build_mission_control.py --hermes-home C:\\approved\\sandbox --dry-run")
terminal(command="py -3 scripts/build_mission_control.py --hermes-home C:\\approved\\sandbox")
```

Resolution precedence is explicit `--hermes-home`, then `HERMES_HOME`, then `~/.hermes`. Prefer the explicit sandbox argument.

## Procedure

1. Read the spec and security boundaries. Complete when the intended home is classified as sandbox or live.
2. Run with `--dry-run`; it reports the destination and makes no writes. Complete when the path ends in `desktop-plugins/hermes-mission-control/plugin.js`.
3. For a sandbox, run without `--dry-run`. Complete when the generated bytes match `templates/plugin.js`.
4. Validate the generated file with `node --check` when Node is available and compare its bytes with `templates/plugin.js`. Complete only when syntax passes and the bytes match.
5. If the destination exists, inspect it. The builder refuses by default; use `--force` only for a deliberate deterministic replacement in the approved home.
6. For a live home, stop and obtain the required greenlight before generation. Enabling or reloading remains a separate user action.

## Pitfalls

- `--force` replaces only this plugin file; it grants no permission to target a live home.
- Profile roster entries are installation metadata, not authoritative per-profile online status.
- Missing values remain `unknown` or `unavailable`; do not reinterpret them as healthy.
- Tasks and Library are `not connected` placeholders, not parallel stores.
- Never add profile paths, profile descriptions, sessions, cron prompts/delivery details, secrets, raw cron objects, or mutation controls.

## Verification

- Dry-run leaves the selected home unchanged.
- First sandbox build creates exactly the expected plugin path.
- A second default build refuses; `--force` reproduces identical template bytes.
- Plugin imports only approved modules, uses no JSX or hardcoded colors, and passes `node --check` when available.
- Review `references/provenance.md` before claiming source fidelity.
