# Codex + Paper MCP Detailed Playbook

## Source and direction lock

Before opening Paper, record:

- exact canonical live URL, including domain variant;
- canonical local product and brand sources;
- optimize-existing vs new-concept vs implementation;
- rejected/historical builds that must not be reused;
- flagship/bonus hierarchy and verified counts;
- claims that remain placeholders.

A new user correction outranks earlier audits and cached captures. Capture the current live page and keep it as a locked reference.

## Recommended Paper structure

Create non-destructively:

1. `00 — Current Reference`
2. `01 — Optimized Desktop`
3. `02 — Optimized Mobile`
4. `03 — Components + Proof Slots`

The prompt must prohibit overwrite, deletion, publication, live-site edits, fabricated proof, and use of rejected directions.

## Evidence-role routing

Classify each asset:

- **Structure:** typography, spacing, components, section sequence.
- **Atmosphere:** mythology, illustration, motion backplates.
- **Product proof:** real UI, command, runtime, file, artifact.
- **Outcome proof:** permissioned person + starting point + build + result + timeframe + source.

Atmosphere may support a proof shell but never fill the proof claim itself.

## Media inspection and placement

Before placing video:

1. Use `ffprobe` for duration, size, codec, dimensions and aspect ratio.
2. Build a contact sheet across opening/middle/payoff/ending.
3. Transcribe audio where available.
4. Note founder/product claims and source requirements.
5. Pick one role: atmosphere, click-to-play overview, founder trust, or product demo.

For a 60–90 second captioned founder overview, prefer click-to-play in/near the hero and a secondary founder-proof placement. Do not let video precede the mobile CTA.

If Paper cannot embed a local MP4, create a poster fallback with:

- actual frame from the source;
- play control;
- duration, language and caption tags;
- exact local path in layer name/annotation.

Never imply that the poster itself plays.

## Progressive build pattern

1. Build full structure with labelled proof/commercial placeholders.
2. Verify desktop section rhythm.
3. Build mobile intentionally.
4. Add brand artwork and real product captures.
5. Add video/poster.
6. Add founder/customer proof through small scoped updates.
7. Add motion last.

This avoids repeating a large design build to change one proof section.

## Claim update pattern

When the user supplies proof:

1. Query canonical knowledge/project sources.
2. Resolve exact amount, period, measurement date and confidentiality.
3. Identify superseded figures and forbid them.
4. Write a small claim-update brief.
5. Update desktop/mobile/components only.
6. Keep evidence-capture slots visible.
7. Verify identical numbers and absent superseded figures through read-only Paper MCP.

## Verification contract

Build session must return:

- Paper file name, ID and stable URL;
- page/artboard names;
- top-level section counts;
- assets embedded vs poster/path fallback;
- remaining placeholders;
- screenshots and tree checks;
- working-lock release;
- exact MCP errors/limits;
- no-overwrite/no-publish confirmation.

Then run a fresh read-only verifier. Ask it to report mismatches only and inspect exact hierarchy, claims, media placement, placeholder survival and desktop/mobile parity.

A remote mutation is complete only when the Paper handle resolves and the artifact has been read back. If a verifier temporarily cannot attach, check Paper app/session state and retry once; report the bounded gap rather than declaring Paper generally unavailable.

## Paper-specific operational notes

- An auto-created empty `Page 1` may resist rename; do not delete it without approval. Create correctly named pages separately.
- Some top-level positioning styles may be ignored while child layout still renders correctly; inspect screenshots rather than treating an ignored style list as automatic failure.
- Export may return no files even when screenshot rendering works; use Paper screenshots and tree summaries for design verification, then report export limitations honestly.
- Always release working-node locks before completion.

## Common failures to prevent

- Wrong domain variant or cached page.
- Replacing an approved live identity instead of optimizing it.
- Bonus visually competing with flagship.
- Decorative art in testimonial/case slots.
- Direct Calendly CTA bypassing an application whose answers are discarded.
- Desktop designed fully, mobile only shrunk.
- Hero CTA below long video.
- Inconsistent proof numbers between breakpoints.
- Historical proof pair surviving in one component.
- Publishing/deleting without explicit approval.

## Handoff checklist

- Paper URL/file ID
- pages/artboards and counts
- asset map
- media source/fallback
- proof claims and sources
- superseded figures excluded
- remaining student/customer/commercial slots
- next recommended video/evidence
- verification result
- greenlight state
